# Обработка изображений

## Конвейер генерации

Запрос проходит конвейер (`app/generatev2`):

1. Разбор URL и валидация (`domain/asset`).
2. Разрешение пресета (если preset URL) в канонический запрос.
3. Проверка политики (deny-by-default) и application-лимитов.
4. Fast-path запроса **оригинала** (`size=x`, без transform, выходной формат = исходному): исходный файл отдаётся как есть — без построения плана, без обработки процессором и **без зачистки метаданных** (EXIF/GPS исходника сохраняются).
5. Поиск готового результата в result-хранилище по каноническому ключу (ReadStream без предварительного Lookup — один round-trip).
6. Keyed singleflight: параллельные запросы того же ассета дедуплицируются — обработка выполняется один раз, остальные ждут результат.
7. Открытие источника из source-хранилища и построение плана обработки — **параллельно** (fan-out/fan-in).
8. Проверка application-лимитов до обработки (размер источника из метаданных объекта, размеры/DPR запроса; `frames`/`duration` на этом уровне не проверяются — см. «Анимации»).
9. Загрузка кэша детекции для `face`/`object`/`face-fix`/`object-fix` (подробнее — в разделе «Детекция лиц и объектов»).
10. Обработка движком (libvips) в spillable-буфер: память с переполнением на диск при исчерпании бюджета `application.buffer-max-bytes`; без фабрики буферов — in-memory chunked-буфер (сегменты 32 KiB, пул переиспользуемых чанков).
11. Post-check application-лимитов (размер выхода → `507 quota`) и публикация в result-хранилище с retry (экспоненциальный backoff 50 мс → 2 с, до 3 попыток для transient-ошибок). В production публикация выполняется **асинхронно** (см. «Асинхронная публикация»): ответ клиенту не ждёт записи в remote.

Канонический ключ кэша — сам canonical URL без хеширования: закэшированный ассет доступен по человекочитаемому имени.

## Асинхронная публикация

В production публикация результата в result-хранилище (кэш) выполняется **фоновыми воркерами** из bounded-очереди, а не на пути ответа клиенту. Это убирает задержку записи в remote (fsync/upload с retry до ~2 с) из критического пути запроса.

Как это работает:

- Ответ клиенту возвращается **сразу** после обработки — данные читаются из refcount-буфера, а задача публикации ставится в bounded-очередь (по умолчанию 512 задач, 4 воркера). Разделяемый буфер удерживает данные, пока открыт хотя бы один reader, поэтому фоновый воркер безопасно читает результат даже после того, как клиент закрыл свой reader.
- Воркер выполняет атомарную публикацию с сохранением прежнего retry/backoff (экспоненциальный, до 3 попыток для transient-ошибок). При исчерпании попыток ошибка логируется и инкрементирует метрику `imager_publish_errors_total`; результат в кэш **не** добавляется (повторный запрос сгенерирует его заново).
- При переполнении очереди (все воркеры заняты) или при завершении работы сервиса публикация выполняется **синхронно** (fallback) — результаты не теряются.
- Ошибка `ErrConflict` (объект уже существует) при повторной публикации того же ассета трактуется как успех: это нормальный сценарий, когда ассет сгенерирован повторно, пока фоновый publish ещё не завершился.
- Waiters keyed singleflight получают результат из общего refcount-буфера (без повторного чтения из remote), поэтому их ответ не зависит от завершения фоновой публикации.

**Известный риск:** сразу после ответа результат может быть **кратко недоступен в кэше** (пока воркер не завершил запись). Повторный запрос того же ассета в этом окне может вызвать повторную генерацию — это безопасно (атомарный publish / NoOverwrite-семантика), но стоит учитывать при горячих «броадкастах» одного URL.

**Graceful shutdown:** при `Shutdown` очередь публикации **дренируется** перед закрытием хранилищ (таймаут по умолчанию 5 с): уже принятые задачи завершаются, после чего останавливаются воркеры. Новые публикации после закрытия выполняются синхронно. Если приложение завершается принудительно (kill -9), возможно, что последние результаты не успеют попасть в кэш — при повторном запросе они будут сгенерированы заново.

## Отказоустойчивость публикации

Очередь публикации — **in-memory**: при `SIGKILL`/crash принятые, но не завершённые задачи пропадают, а drain при `Close` ограничен 5 с. WAL-журнала нет. Вместо него используется **ленивое самовосстановление** на чтении: потеря публикации не является необратимой.

Порядок записи гарантирует это:

1. **Метаданные пишутся ДО публикации.** Sidecar-метаданные ассета (`created_unix`, `largest_ai_asset`, боксы детекции) записываются в `processAndPublish` **до** ветки async/sync публикации ([`service.go`](app/generatev2/service.go)). Детекция (`ensureDetections`) сохраняет боксы в sidecar ещё раньше — в `generateLocked`, до обработки.
2. **«Метаданные есть, ассета нет» = недоопубликованный ассет.** Если процесс упал после записи метаданных, но до `Publish` (или publish упал с ошибкой), в result-хранилище остаётся состояние «sidecar есть, ассета нет».
3. **Повторный запрос восстанавливает ассет.** `tryCache` даёт промах (ассета в кэше нет) → запускается обычный путь генерации. Но `ensureDetections` при `Load` находит уже записанные боксы и **не вызывает модель повторно** (инвариант «1 вызов модели на родителя»). Обработка (libvips) перевыполняется, результат публикуется — ассет снова доступен.

Таким образом, потеря при `SIGKILL`/crash **самовосстанавливающаяся**: следующий запрос того же ассета регенерирует его, переиспользуя дорогие результаты ИИ-детекции. Цена — повторная обработка изображения (без повторного вызова модели). Это осознанный компромисс: полноценный startup-reconciler (enumerate недоопубликованных ассетов при старте) потребовал бы пере-генерации **всех** ассетов с повторной обработкой на старте (без лимита — опасно, с лимитом — бесполезен), поэтому он не реализован.

Интеграционный тест сценария — `TestGeneratePublishLossRecalRecalizesFromMetadata` ([`publish_recovery_test.go`](app/generatev2/publish_recovery_test.go)): симуляция потери публикации (publish возвращает `ErrUnavailable`) → повторный запрос регенерирует ассет, детектор вызывается ровно один раз суммарно, ассет в итоге доступен.

## Операции

Операция (resize/crop/smart-crop/face-crop/object-crop/face-fix-crop/object-fix-crop) задаётся **только** полем `crop` пресета/custom; `trim` — независимый фильтр; сегмент URL — имя пресета или custom-имя (размер-грамматика, например `640x`, `x400`, `120x80`, `x`).

Порядок применения: **auto-orient (при загрузке) → rotate → flip → trim → crop/resize**. EXIF auto-orient выполняется на этапе декодирования (import), ручные rotate/flip — сразу после загрузки, строго до trim и кропа/ресайза.

Кроп (все режимы, кроме resize) требует **оба измерения** целевого размера: для размеров с одной осью (`x400`, `640x`) операция автоматически понижается до resize (trim при этом сохраняется).

### Resize (`crop: ""`)

Размер из URL-грамматики умножается на DPR:

```text
/test-jpg/640x.webp     custom 640x: ширина 640, высота пропорционально
/test-jpg/x400.webp     custom x400: высота 400
/test-jpg/120x80.webp   custom 120x80: точный размер
/test-jpg/x.webp        custom x: исходный размер (конвертация формата)
```

Поведение зависит от того, сколько осей задано:

- **Одна ось** (`640x`, `x400`): пропорциональный resize без заполнения — холст равен результату (вторая ось вычисляется из пропорций кадра).
- **Обе оси** (`120x80`): изображение вписывается пропорционально в бокс `W×H` (fit, без кропа), затем недостающие края заполняются до **точного** `W×H` (letterbox/pillarbox):
  - если альфа возможна (выходной формат поддерживает альфу — PNG/APNG/WebP/GIF/AVIF/HEIF/JPEGXL — или исходник имеет альфа-канал) — поля **прозрачные**;
  - иначе (формат без альфы, например JPEG) — поля заливаются цветом `processing.default-resize-background` (hex `"#RRGGBB"`); при пустом значении — белый `"#ffffff"`.

Для анимаций resize+letterbox выполняется покадрово (каждый кадр вписывается и дополняется до `W×H` независимо).

Custom с суффиксом `@N` в имени (например `120x80@2` — реально 240×160) разрешается так: либо в конфигурации есть точный custom с именем `120x80@2` (или `dpr: N`), либо custom с базовым именем `120x80` **без установленного dpr** — тогда DPR берётся из URL. Если у custom dpr задан явно, `@N`-суффикс в URL с другим значением запрещён (403). Явные значения `@dpr` в URL — только 2 и 3 (правила dpr — [CONFIGURATION.md](CONFIGURATION.md#правила-dpr)).

### Crop (`crop: center`)

Центрированная обрезка под целевой размер.

### Smart-crop (`crop: smart`)

Обрезка по attention-области (libvips). Требует сборки с `-tags libvips`.

### Trim (`trim: true`)

Обрезка однотонных полей перед кропом/ресайзом. Настройки глобальные (`processing.default-trim-*`):

- `default-trim-mode`: `auto` — цвет фона определяется по краевому пикселю; `color` — фиксированный `default-trim-color`;
- `default-trim-tolerance`: допуск сравнения `[0,1]`.

### Face-crop (`crop: face`) и Object-crop (`crop: object`)

Обрезка по bounding box детекции: окно зумится в область лица/объекта (bbox + margin расширяется до аспекта цели — лицо занимает стабильную долю кадра) и центрируется на ней с clamp к границам. Требуют сборки с `-tags libvips,onnx`, C-библиотеки ONNX Runtime и настроенных моделей. Если детектор не сконфигурирован (пустой путь модели или сборка без `-tags onnx`), запрос завершается ошибкой обработки `500 processing` (не `501`: `501 unsupported_format` возвращается только когда формат вне покрытия движка).

### Face-fix (`crop: face-fix`) и Object-fix (`crop: object-fix`)

Cover-масштаб **без зума** в лицо/объект. Изображение масштабируется ровно до целевого размера (cover), а обрезается ТОЛЬКО по оси, пропорционально избыточной в оригинале:

- оригинал «шире» цели (imgW/imgH > targetW/targetH) — масштаб по высоте, окно = (targetW/scale) × imgH: полная высота сохраняется, кроп только по X;
- оригинал «выше» — масштаб по ширине, окно = imgW × (targetH/scale): полная ширина сохраняется, кроп только по Y;
- аспекты равны — окно = весь кадр.

Позиция окна по избыточной оси — центр области детекции (union bbox всех лиц/объектов + `detection.margin`), с clamp к границам оригинала (лицо у края — окно упирается в край, лицо остаётся смещённым, но не обрезается). Нет детекции — центральное позиционирование (эквивалент `crop: center`). Требования к сборке/моделям те же, что у `face`/`object`.

## Ориентация

| Параметр | Значения | Действие |
|----------|----------|----------|
| `auto-orient` | bool (дефолт `true`) | Автоповорот по EXIF Orientation — фото с камер отображаются правильно |
| `rotate` | `""`/`none`/`90`/`180`/`270` | Фиксированный поворот по часовой стрелке |
| `flip` | `""`/`none`/`horizontal`/`vertical` | Отражение слева-направо / сверху-вниз |

Значения задаются глобально (`processing.default-*`) и переопределяются в пресетах (`auto-orient`, `rotate`, `flip`; `"none"` явно отключает глобальный дефолт). EXIF-метаданные удаляются из результата (см. «Метаданные и приватность»).

## Водяные знаки

Водяной знак описывается в секции `watermarks` (map: ключ = имя ватермарки) и применяется по имени. Приоритет: пресет/custom (поле `watermark`) → `processing.default-watermark`.

```yaml
watermarks:
  logo:
    path: "/etc/imager/watermarks/logo.png"
    position: center        # top | bottom | left | right | center
    repeat: no-repeat       # no-repeat | repeat | repeat-x | repeat-y | round | space
    size: contain           # contain | cover | "" (исходный размер) | "200px 50px" | "200px" | "50%" | "50"
    opacity: 100            # 0-100; 100 = непрозрачный (по умолчанию), 0 = полностью прозрачный
```

Семантика полей соответствует CSS `background-position` / `background-repeat` / `background-size`.

Форматы `size`:

- `contain` — вписать копию в холст с сохранением пропорций;
- `cover` — покрыть холст копией; излишек обрезается **по позиции** (`position`): `center` срезает излишек равномерно с обеих сторон, `left`/`right`/`top`/`bottom` — с противоположного края;
- пустое значение — копия накладывается в **исходном** (натуральном) размере файла знака;
- `"{w}px {h}px"` — фиксированный размер в пикселях;
- `"{w}px"` — фиксированная ширина, высота пропорциональна аспекту файла знака;
- `"{n}%"` (и `"{n}"` — число без суффикса) — ширина и высота копии = `n`% соответствующих измерений холста (аспект знака игнорируется); `n` в `[1,100]`.

При `dpr > 1` холст масштабируется на `dpr`, поэтому фиксированные (`px`) и натуральные размеры копии умножаются на `dpr` — ватермарка выглядит одинаково при любом `dpr`. `contain`/`cover`/проценты зависят от холста и масштабируются автоматически.

Прозрачность задаётся полем `opacity` в процентах: `100` — знак непрозрачный (по умолчанию, если поле не указано), `0` — полностью прозрачный (невидимый). Значения вне диапазона [0,100] заменяются на `100`. Прозрачность реализуется умножением альфа-канала знака на множитель `opacity/100` перед композитом; цветовые каналы не затрагиваются. При `opacity: 100` операция пропускается (нулевые накладные расходы); для знака без альфа-канала он добавляется (AddAlpha) перед масштабированием прозрачности.

Поведение:

- libvips реализует position/repeat/size полностью;
- `cover` + `no-repeat`: копия может быть больше холста; видимый фрагмент вырезается по позиции (`CoverOffset`) и композитится в точку пересечения — излишек обрезается с нужной стороны (для `repeat`-режимов при oversized-копии сохраняется прежний clamp-путь);
- при `dpr > 1` фиксированные (`px`) и натуральные размеры копии умножаются на `dpr`, чтобы ватермарка выглядела одинаково при любом `dpr`;
- на анимированных изображениях (GIF/WebP/HEIF/APNG/AVIF — любой анимированный вход) водяной знак накладывается **на каждый кадр** с сохранением delay/loop (`compositeWatermarkPerFrame`); размер и раскладка копий вычисляются относительно размеров **одного кадра**, а не сшитого холста;
- все копии repeat/tile-раскладки накладываются одним composite-вызовом (`CompositeMulti`);
- защитный лимит тайлинга: число копий проверяется до материализации раскладки; при `repeat` с крошечным знаком на большом холсте (> 4096 копий) запрос завершается ошибкой обработки (защита от патологической аллокации).

Файл водяного знака обязан существовать на старте, иначе конфигурация отклоняется. Байты файла кэшируются в памяти (LRU по числу файлов и суммарному размеру, TTL, инвалидация по mtime/размеру, singleflight на загрузку; дефолты: 32 файла, 64 MiB, TTL 5 мин; настраивается `libvips.watermark-cache.*`). При любом промахе кэша выполняется чтение с диска — ошибка кэша не ломает запрос.

## Детекция лиц и объектов

Детекция выполняется ONNX-моделями внутри процесса (требуется сборка с `-tags libvips,onnx`):

| Модель | Операция | Назначение |
|--------|----------|------------|
| YuNet (`face-model`) | `face`, `face-fix` (с `trim: true` или без) | Детекция лиц |
| SSD/YOLO-подобная (`object-model`) | `object`, `object-fix` (с `trim: true` или без) | Детекция объектов |

```yaml
detection:
  face-model: "/etc/imager/models/face_detection_yunet_2023mar.onnx"
  object-model: "/etc/imager/models/ssd_mobilenet.onnx"
  confidence-threshold: 0.5   # порог уверенности [0,1], боксы ниже отбрасываются до NMS
  max-objects: 5              # максимум объектов после NMS
  margin: 0.1                 # отступ вокруг бокса как доля его размера (10%)
```

Свойства:

- модели загружаются лениво при первом запросе и кэшируются в памяти; отсутствие файла модели — ошибка при первом обращении, а не при старте;
- результаты детекции кэшируются в sidecar-хранилище метаданных (`metadata.*`): модель вызывается ровно один раз на ассет-результат (sidecar лежит рядом с ассетом; для видео — рядом с извлечённым кадром `x.jpg`), последующие запросы читают боксы из кэша. Кэш инвалидируется по отпечатку источника (size + mtime; для извлечённых кадров — SHA-256);
- детекция на уровне приложения (app-level) выполняется по RGB-пикселям **оригинала без trim**; при комбинации с `trim: true` боксы транслируются на trim-offset внутри процессора перед кропом;
- ONNX-инференс выполняется вне libvips-слота (отдельный detection-семафор, handoff-схема): дефолтная конкурентность `max(1, GOMAXPROCS/2)`, бюджет ожидания `libvips.detection.max-wait` (дефолт 5 с);
- **graceful degradation при перегрузке AI-детекции**: если detection-семафор перегружен (переполнение очереди ожидания или истечение `libvips.detection.max-wait`), запрос НЕ получает ошибку 503, а деградирует к fallback-фокусировке — center-crop (эквивалент `crop: center` без smart-focus). Событие логируется (warning) и учитывается счётчиком `imager_detection_degraded_total`. Такая деградация не кэшируется в sidecar как «проверено, пусто»: боксы не записываются, следующий запрос снова попробует модель. Ошибки самой модели (сбой ONNX-инференса) остаются ошибками обработки.

## Анимации

Анимированные форматы: GIF, WebP, HEIF, APNG, AVIF (вход APNG читается как анимированный PNG; запись APNG — см. «Движки»; AVIF — анимация через HEIF-контейнер, libvips heifsave пишет multi-page изображения как последовательность кадров).

Поддерживается:

- ограничение числа кадров (`frames` в пресете): применяется на этапе **загрузки** (NumPages) — загружается не более N кадров. `application.limits.frames`/`duration` на application-уровне фактически не проверяются (в pre-check передаются нули) — ограничение действует только через `frames` пресета;
- ограничение длительности (`duration`, мс): поле плана существует, но **пока не реализовано** в движке (ограничение кадров после загрузки оставлено на будущее) — значение игнорируется;
- зацикливание (`loop`: nil = оставить как в исходнике, true = бесконечно (loop=0), false = однопроходно (loop=1));
- delay кадров сохраняется из исходника автоматически.

Покадровая обработка (кроп, вертикальный flip, ватермарка) выполняется с разборкой вертикального стека кадров и восстановлением метаданных анимации (page-height, n-pages, delay, loop).


## Качество и сжатие

Конфигурация кодирования (единая top-level секция `encoders`, якорный автомаппинг, приоритеты) — [CONFIGURATION.md](CONFIGURATION.md#encoders). Здесь — как `quality` превращается в параметры кодека.

**Скалярный `quality`** пресета (0–100; 0 = `encoders.default-quality`) действует по типу формата:

- **Lossy-форматы** (jpeg/webp/avif/heif/jxl): `quality` передаётся кодеру **напрямую** как качество потери (число качества запроса/пресета = качество выхода). Чем выше — тем больше битов, меньше артефактов; чем ниже — тем меньше размер.
- **Lossless-форматы** (png/apng/gif): потерь `quality` **никогда не вводит**. Он управляет **усилием упаковки** (compression-level/effort) и **палитровой автоматикой** через якорный автомаппинг — «спрятать» качество в меньший файл: больше `quality` → плотнее упаковка, при `q≥90` PNG-палитра автоматически выключается (truecolor, защита градиентов).

Per-format переопределение качества — **только нативными параметрами**: `webp-quality`, `jxl-quality` и т.п. (только lossy) либо ключами усилия (`webp-reduction-effort`, `jxl-effort`, `gif-effort`, `png-compression-level` и т.д.). Per-format качество для lossless-форматов (`png-quality`) — ошибка конфигурации.

Приоритеты параметров на каждом экспорте (разрешаются через `domain/encoding.Resolve` на каждый экспорт):

> **preset override (плоские нативные ключи) > `encoders` YAML > якорный автомаппинг от quality > реестровый дефолт**

Качество экспорта: **per-format quality пресета > `encoders.<формат>.quality` > скалярный `quality` (`0` = `encoders.default-quality`)**.

### Соответствие quality → параметры

Автомаппинг применяется только когда параметр не задан ни в пресете, ни глобально в `encoders` (заданный ключ — explicit override, отменяет формулу):

| Формат | Параметр | Диапазон | Якорь ↦ значение |
|--------|----------|----------|------------------|
| webp | `reduction-effort` | `[0,6]` | q75→4, q100→6, q0→0 |
| avif | `speed` | `[0,9]` | q80→6, q100→0, q0→9 (инверсия: меньше = медленнее, лучше сжатие) |
| jxl | `effort` | `[3,9]` | q75→7, q100→9, q0→3 |
| gif | `effort` | `[1,10]` | q75→7, q100→10, q0→1 |
| png | `compression-level` | `[1,9]` | q85→6, q100→9, q0→1 |
| png | `palette` | bool | q<90 → ON, q≥90 → OFF (truecolor) |
| png | `palette-colors` | `[2,256]` | q85→256, q0→2 |
| png | `palette-bit-depth` | `[1,8]` | из `palette-colors`: ≤2→1, ≤4→2, ≤16→4, иначе (17–256)→8 |

Якорь = качество, при котором нативные параметры дают текущее дефолтное поведение движка (webp/jxl/gif — 75, jpeg/avif/heif — 80, png/apng — 85); при отклонении от якоря параметры масштабируются линейно к границам диапазона.

## Лимиты обработки

Три слоя защиты (значения — [CONFIGURATION.md](CONFIGURATION.md)):

1. **Application** (`application.limits`): размер источника/выхода, размеры, DPR, кадры, длительность, concurrency — проверяются независимо от политики до и после обработки.
2. **Движок**: libvips `limits.*` (timeout, output-bytes, concurrency, threads, cache).
3. **HTTP-слой**: context deadline (`http.generate-timeout` → `504`), admission control (`http.max-concurrent-requests` → `503`).

Перегрузка процессора (переполнение очереди слотов) возвращает клиенту `503 overloaded` с `Retry-After` (по умолчанию `1`, настраивается через `http.retry-after`).

## Исходы генерации (outcome-коды)

Use case `app/generatev2` возвращает типизированные ошибки `OutcomeError` с категорией исхода; HTTP-слой маппит их в статусы:

| Outcome | HTTP | Когда возникает |
|---------|------|-----------------|
| `invalid` | `400` | Невалидный запрос/план, неразрешимый пресет (`preset_not_found`) |
| `forbidden` | `403` | Политика deny-by-default, превышение application-лимита (pre-check) |
| `not_found` | `404` | Исходник или результат не найден |
| `quota` | `507` | Превышение квоты хранилища или `application.limits.output-bytes` (post-check) |
| `unavailable` | `503` | Хранилище/координатор временно недоступны (с `Retry-After`) |
| `overloaded` | `503` | Перегрузка процессора/HTTP-семафора (с `Retry-After`) |
| `processing` | `500` | Ошибка обработки изображения (в т.ч. недоступная детекция, превышение лимита тайлов ватермарки) |
| `canceled` | `504` | Отмена/таймаут контекста (`http.generate-timeout`) |

Отдельно: формат вне покрытия движка (например, APNG-выход без libspng) маппится в `501 unsupported_format` до разбора OutcomeError.

## Passthrough fast-path

Если план ничего не меняет (выходной формат совпадает с исходным, размер уже целевой или `size=x`, нет watermark/trim/детекции/ручной ориентации, EXIF Orientation нейтрален (0/1), нет ограничения кадров/loop, DPR нейтрален, в исходнике нет метаданных вне технического allowlist и ICC-профиль допустим политикой цвета), исходные байты возвращаются **как есть** — без decode/encode. Решение принимается по лёгкому заголовку файла; при любых сомнениях выполняется полная обработка. Следствие: passthrough не зачищает метаданные — но и полный конвейер в этой ситуации ничего бы не удалил (allowlist содержит только технические поля, которые конвейер сохраняет).

## Цвет, DPI и метаданные

- **ICC color management** (`processing.color`): `strip` (дефолт) — ICC-профиль удаляется при экспорте; `transform` — embedded-профиль конвертируется в sRGB (через PCS, lcms) **до** пиксельной обработки; CMYK без профиля обрабатывается fallback-профилем sRGB; `keep` — embedded-профиль сохраняется в выходе. Fast-path: sRGB-совместимые профили (проверка по сигнатуре/имени без lcms) и изображения уже в sRGB не конвертируются. Ошибка lcms не роняет запрос — fallback на strip с warning-логом.
- **DPI-нормализация**: перед экспортом xres/yres сбрасываются к 72 DPI, если исходник содержит значимое иное разрешение (96/144/300 DPI и т.п. — сканы, принт). Изображения без DPI-метаданных (xres/yres ≈ 0/1) не перекопируются.
- **Metadata stripping**: перед экспортом принудительно удаляются все пользовательские метаданные (EXIF/GPS, XMP, IPTC, комментарии) для **всех** форматов (defense-in-depth: heifsave/jxlsave не поддерживают опцию strip). Технические поля, необходимые для корректного отображения (orientation, n-pages, page-height, delay, loop), сохраняются; orientation к этому моменту уже применён при загрузке.
- **Shrink-on-load**: для JPEG/WebP при значительном уменьшении используется предварительное уменьшение при декодировании (jpeg shrink / webp scale) — дешевле, чем декодировать полный размер. Управляется `libvips.shrink-on-load` (по умолчанию включён); не применяется при ручной ориентации, детекции и точных кропах, где важна точность.

## Видео-источники

Ассет из видео (mp4/webm/mov/mkv/avi/m4v) генерируется из **одного кадра**:

1. Если в sidecar-метаданных видео уже зафиксирован кадр (`x.jpg` рядом с видео, ключ `<path>/<name>-<fmt>/x.jpg`), источником служит он — оригинал видео не открывается.
2. Иначе кадр извлекается через ffmpeg/ffprobe (`adapters/videoframe/ffmpeg`): ffprobe определяет длительность/fps/размеры, ffmpeg извлекает JPEG на проценте длительности (`video.frame-percent`, дефолт 50) с уменьшением до 1920 px по ширине. Кадр проверяется на контрастность (stddev яркости/255 ≥ `video.min-contrast`); при неудаче перебираются следующие кадры (шаг `video.frame-step`, дефолт 1, до `video.attempts` попыток, дефолт 3); если ни один не прошёл — возвращается последний.
3. Извлечённый кадр асинхронно сохраняется как `x.jpg` и фиксируется в метаданных; обработка кадра идёт по обычным правилам (исходный формат для плана — JPEG).

Оригинал видео отдаётся как есть через fast-path оригинала (`size=x`, формат совпадает). Извлечение выполняется на detached-контексте с таймаутом 60 с: разрыв клиента не прерывает ffmpeg-работу.

## Learning-mode

Runtime-флаг (`app/learning.Controller`); включается только через `policy.learning-mode: true` в конфигурации с последующим перезапуском (runtime-переключателей и admin-эндпоинта нет, см. [CONFIGURATION.md](CONFIGURATION.md#policylearning-mode)). При включённом режиме:

- запрос, не подходящий по правилам политики, всё равно генерируется, если сегмент — размер-грамматика (`120x60`) или имя глобального пресета: он разрешается дефолтными настройками (resize, размер из сегмента, DPR из URL или 1) либо настройками реального пресета;
- результат **отдаётся клиенту, но не сохраняется** в result-хранилище (без публикации, `largest_ai_asset` и `created_unix`);
- имя несуществующего пресета (не размер, не глобальный пресет) остаётся `403` — в path-policies такие записи не попадают.

Наблюдения режима используются для автоматического пополнения `policy.path-policies` в `setting/generate-local.yaml`.

## Регистрозависимость

Канонизация URL (`domain/asset`) нормализует **регистр форматов** (source и output) к нижнему: расширения файлов изображений регистронезависимы, поэтому `/a.PNG` и `/a.png` — один и тот же ассет и один cache-ключ. Регистр `source_name` и `segment_name` **сохраняется** — он семантически значим (имена исходников/пресетов могут различаться регистром).

**Известное ограничение:** на case-insensitive файловых системах (Windows/macOS по умолчанию) имена исходников/сегментов, различающиеся только регистром (`Banner` vs `banner`), указывают на один и тот же файл, но создают **разные** cache-ключи. Это безопасно (нет коллизии ключей), но может приводить к дублированию кэш-объектов и повторной обработке. Если требуется строгая дедупликация на таких ФС, нормализуйте регистр имён исходников на уровне хранилища/конфигурации — на уровне канонизации это осознанно не делается.
